## Approach — Slide 1: What is our network?

### Slide text

**Title:** Our Network: Routers, Links, and Traffic

- **Nodes** = routers. Each router connects one core and its slice of memory.
  - Tree also has 15 extra "switch-only" routers that just forward traffic.
- **Links** = two-way on-chip wires: 1 packet per cycle, 1-cycle delay.
- **4 topologies, 16 cores each:** Mesh 4×4 · Torus 4×4 · Ring · Binary Tree
- **Input data** = synthetic traffic from gem5/Garnet:
  - *Traffic pattern* = who sends to whom (8 patterns: uniform random, transpose, bit-complement, neighbor, ...)
  - *Injection rate* = how often each core sends (0.025 → 0.8 packets/cycle)

*[Image: `figures/networks.png` — links colored by edge betweenness]*

| | Mesh | Torus | Ring | Tree |
|---|---:|---:|---:|---:|
| Routers | 16 | 16 | 16 | 31 |
| Links | 24 | 32 | 16 | 30 |
| Diameter (hops) | 6 | 4 | 8 | 8 |
| Avg hops between cores | 2.67 | 2.13 | 4.27 | 6.53 |

### Speaker notes (~45 s)

> "We model each network-on-chip as a graph. A **node is a router**, and every router has one processor core and its piece of memory attached. The only exception is the tree: the cores sit at the 16 leaves, and the 15 routers above them only forward traffic. An **edge is a physical wire** between two routers. It's two-way, carries one packet per cycle, and takes one cycle to cross.
>
> We built four 16-core topologies: mesh, torus, ring, and binary tree. gem5 only ships the mesh, so we wrote the ring, torus, and tree ourselves.
>
> Our input data is **synthetic traffic generated by gem5's Garnet network model**. Two knobs define it. The *traffic pattern* says who talks to whom; for example, in transpose, core (x,y) sends to (y,x). The *injection rate* says how often each core sends. We use all 8 of Garnet's patterns and sweep the rate from very light to very heavy.
>
> The link colors show edge betweenness, meaning how many shortest paths use that link. Notice the tree: the links near the root are bright because almost all traffic has to cross them. That will matter in our results."

### If asked

- **Why 16 cores?** Garnet's traffic patterns assume a square, power-of-two core count. 16 is fast for a first sweep; we'll scale to 64 for the final.
- **Why does the torus have more links than the mesh?** Wrap-around links at the edges: 32 vs. 24. That's also why its diameter drops from 6 to 4.
- **What is a flit / packet here?** We use 1-flit control packets (128 bits) so that packet length doesn't mix into the results. We'll add 5-flit data packets later.

## Approach — Slide 2: Main steps

### Slide text

**Title:** Approach: Predict from the Graph, Then Check in the Simulator

1. **Build** each topology in gem5/Garnet (we wrote Ring, Torus, Tree)
2. **Analyze the graph** (Python + NetworkX)
   - Diameter, average hops, betweenness, connectivity
   - **Prediction:** latency ∝ hops; network saturates when its **busiest link** fills up
3. **Simulate** every topology × traffic pattern × injection rate
   - 4 × 8 × 32 = **1,024 gem5 runs**
   - Record latency, hops, packets delivered, link usage
4. **Compare** prediction vs. simulation → explain *why* each topology wins or loses
5. **Connect to real chips** (Intel mesh, AMD chiplets, Google TPU torus)

*Suggested visual:* a simple flow diagram

```
            ┌─> Graph analysis ──> Predictions ──┐
Topology ───┤                                    ├──> Compare & explain ──> Real-chip case study
            └─> gem5 simulation ─> Measurements ─┘
```

### Speaker notes (~45 s)

> "Our approach has two parallel tracks that meet in the middle.
>
> In the **graph track**, we use NetworkX to compute structural properties of each topology: diameter, average hop count, and betweenness. From those we make two predictions. First, when the network is lightly loaded, latency should depend only on how many hops a packet travels. Second, as load grows, the network saturates when its **busiest link** is full, so the maximum throughput should be one divided by the traffic on that link.
>
> In the **simulation track**, we run gem5 for every combination of topology, traffic pattern, and injection rate. That's 1,024 simulations, which takes about six minutes on a laptop with our sweep script.
>
> Then we **compare** the two. Where they agree, the graph explains the performance. Where they disagree, the disagreement tells us something the graph is missing. Finally, we connect our findings to real chips.
>
> The prior work we showed compared topologies but didn't explain the differences with graph metrics. This comparison step is what we add."

### If asked

- **How exactly is the "busiest link" computed?** For every sender/receiver pair, we follow the path the routing rule would choose and add that pair's traffic to every link on the path. The link with the largest total is the bottleneck. Predicted saturation = 1 ÷ that total (capped at 1). This comes from Dally & Towles, *Principles and Practices of Interconnection Networks*, Ch. 3.
- **Which routing does each topology use?** Mesh and torus go X first, then Y. Ring takes the shorter direction. Tree goes up to the common ancestor and back down; there is only one path.

## Preliminary Results — Slide 3

### Slide text (minimal, since the figure does the talking)

**Title:** Preliminary Results: The Graph Predicts Performance — Until Deadlock

*[Image: `figures/prelim_results.png`]*

- **Low load:** latency = 2 × hops + 5 cycles for *every* topology and pattern (R² = 1.00)
- **High load:** busiest-link prediction matches gem5 within **~5%** (20 cases)
- **Ring deadlocks** at 0.275 packets/cycle, half its bandwidth limit (0.5)

### What each panel shows (for you)

| Panel | What it shows | Key number |
|---|---|---|
| **A. Latency vs. load** (uniform random) | Each curve is flat, then shoots up at saturation. Order of saturation: Tree first (0.2), Ring (~0.275, deadlock), Mesh (~0.6), Torus last (~0.73) | Torus handles about 3× the load of a Tree |
| **B. Low-load latency vs. hops** | All 32 topology × pattern combos lie on one straight line | latency = 2.01 × hops + 5.0, R² = 1.000 |
| **C. Predicted vs. simulated saturation** | Points on the dashed line = graph prediction was right | Tree bit-complement: predicted 0.125, measured 0.125. Mesh bit-complement: 0.5 vs 0.5 |

### Speaker notes (~60 s)

> "Here are our preliminary results from all 1,024 simulations.
>
> **Panel A** shows latency as we increase load, for uniform random traffic. Every curve is flat and then shoots up; that's saturation. The tree saturates first, then the ring, then the mesh. The torus lasts the longest, handling roughly three times the load of the tree.
>
> **Panel B** explains the flat part. At low load, latency is exactly 2 cycles per hop plus 5 cycles of fixed overhead, across every topology and every pattern. That's an R² of 1. So at low load, **average hop count, a pure graph metric, fully explains latency**. The torus is fastest simply because its wrap-around links make paths shorter.
>
> **Panel C** explains when it shoots up. On the x-axis is our graph prediction, one over the load on the busiest link. On the y-axis is where gem5 actually saturated. Most points sit right on the line, within about 5%. For example, under bit-complement every tree packet must cross the root, so we predicted the tree would saturate at one-eighth. gem5 measured exactly one-eighth.
>
> The one big outlier is the **ring under uniform traffic**. It should handle 0.5 but stops at 0.275, because it **deadlocks**. That's a failure the graph alone can't predict, and it leads to our challenges."

## Challenges, Anticipated Difficulties, and Solutions (talk through these verbally)

Pick 2–3 of these depending on time. The first two are the strongest.

### 1. The ring deadlocks (main challenge)

- **What happened:** above 0.275 packets/cycle under uniform traffic, the ring delivered almost nothing (about 1,200 of about 96,000 packets). Packets going around the ring each wait for a buffer held by the next packet, forming a circle where nothing can move.
- **Why the graph missed it:** our graph model only counts link *bandwidth*. Deadlock is about *buffer dependencies* between packets, which isn't in the graph.
- **Solution:** the standard fix is a **"dateline"** (Dally & Seitz, 1987): packets switch to a second set of buffers (virtual channels) when they cross a fixed point on the ring, which breaks the cycle. Garnet has no built-in support, so we'll add it in Garnet's C++ code (`OutputUnit::select_free_vc` and the custom routing hook in `RoutingUnit.cc`). The torus has the same risk on its wrap-around rings, so the same fix protects it.

### 2. Real routers don't reach the ideal limit

- **What happened:** the graph says a 4×4 mesh and torus could each take up to 1.0 packets/cycle under uniform traffic, but gem5 saturates at about 0.6 (mesh) and 0.75 (torus). The torus points in panel C also sit a bit below the line.
- **Why:** the graph ignores the router's internal hardware. Packets compete for the router's internal switch and buffers every cycle, and some cycles are lost to that contention.
- **Solution:** measure this "router efficiency" factor and check whether one number works for all topologies. Test whether more virtual channels (buffers) close the gap.

### 3. Simulator settings that silently give wrong answers

- **What we found:** gem5's `--sim-cycles` is actually measured in picoseconds, so `10000` simulates only 10 cycles. The traffic generator also runs at 1 GHz while the network runs at 2 GHz by default, so "packets per cycle" would mean two different things.
- **Solution:** we run both at 1 GHz and convert units in our scripts. We validated the setup by checking that simulated hop counts match the graph's shortest paths exactly (Mesh 2.50, Torus 2.00, Ring 3.97, Tree 6.12).

### 4. Traffic patterns assume a grid

- **What we found:** Garnet defines patterns like "neighbor" and "transpose" using 4×4 grid coordinates. On a ring or tree, a "neighbor" may be several hops away.
- **Solution:** keep it (all topologies get the same logical traffic, which is a fair comparison), but state it clearly. Possibly add patterns defined by physical distance.

### 5. Measuring throughput correctly

- **What we found:** "average packets delivered" can look higher than the bottleneck allows, because cores whose traffic doesn't cross the bottleneck keep delivering.
- **Solution:** define saturation as the first injection rate where latency exceeds 3× its low-load value, or delivered traffic falls below 95% of offered traffic. That definition is what made the predictions line up.

### Anticipated difficulties ahead

| Difficulty | Plan |
|---|---|
| Scaling to 64 cores (more runs, slower) | The sweep script runs in parallel; 1,024 runs take 6 min at 16 cores, so 64 cores should still be under an hour |
| Implementing deadlock-free routing in Garnet's C++ | Start with the ring (1-D) before the torus; check with a long run past saturation |
| Graph metrics that don't scale to irregular networks | Compare which metric (hops, betweenness, bisection) predicts best across all topologies |

## How to reproduce (for the report)

```bash
# one-time: build gem5 (about 5 min on an M-series Mac)
cd gem5
CXX=$PWD/../clang++-sdk scons defconfig build/NULL build_opts/Garnet_standalone
CXX=$PWD/../clang++-sdk scons build/NULL/gem5.opt -j10
cd ..

# simulations (about 6 min) and figures
python scripts/sweep.py --rates $(seq 0.025 0.025 0.8) --out results/prelim_fine.csv
python analysis/prelim_results.py results/prelim_fine.csv
python analysis/plot_networks.py
```

Requires `pip install networkx numpy scipy pandas matplotlib scons`.
